# Public demo gateway

Cloudflare can [convert cold-cache HEAD to GET](https://developers.cloudflare.com/cache/concepts/cache-behavior/), invalidating a signature bound to HEAD. Caller cache bypass alone did not prevent the hosting CDN's conversion. For HEAD on approved public files only, the gateway explicitly signs/fetches GET with identity encoding, cancels the body, and returns native origin headers/status without a body. Range/If-Range are ignored for this metadata request, while conditional headers remain supported. Private/API HEAD, mutations and video range GETs retain their original methods. No media slicing or signature exception is added. Signed origin subrequests use `cache: 'no-store'`; native Pages caching remains unchanged. Acceptance must send HEAD with fresh keys before any warming GET. Warm-cache success alone is insufficient.

The public demo is https://dexter-onboardflow.pages.dev/. The .NET application and database remain on their existing hosts. The original exact-IP scheme trust proved brittle; a homepage response alone also did not establish a working session on the previous host.

This small Cloudflare Pages Worker signs the timestamp, canonical public origin, HTTP method, encoded target and body digest with ECDSA P-256. Only Cloudflare holds the private signing key in `EDGE_SIGNING_KEY`; the application ships the public verification key. Caller-supplied forwarding and OnboardFlow edge headers are replaced. The application accepts HTTPS evidence only from a valid, recent signature and retains secure cookies, CSRF, owned sandboxes, command replay protection and the existing inference budget. Proxy IP addresses can change without breaking that identity check.

For private API/database-readiness requests the Worker overwrites internal `__of_network` query metadata with a keyed daily hash of the Cloudflare-supplied visitor address (IPv6 /64). HKDF derives an independent HMAC key using the existing protected gateway key and a fixed purpose; there is no additional secret binding. The existing encoded-target signature binds the network hash without a second signature or public URL change. The app trusts only this verified metadata, never a visitor-supplied IP or header. Raw IP addresses are not stored in the application counters. Ordinary public assets/media retain their original routing and native metadata/range behavior.

Application delivery checks the live gateway source SHA-256 before publishing Hostless. The packager stamps this stable source fingerprint in `X-OnboardFlow-Gateway-Hash`, separately from the diagnostic app asset revision. This remains safe across cancelled builds and lets backend-only releases reuse identical checked gateway code without another promotion. Caller metadata is compatible with older app images, so Pages can safely be promoted first. The new app rejects missing/malformed signed network metadata on private API/readiness routes. Apply additive database migrations before publication; do not roll back to an image that ignores owner revocations without first disabling its owner verifier.

The production image enables `VerifiedEdge__Enabled`. Unsigned original-host page requests redirect to the public demo; unsigned mutations are rejected. The host's unauthenticated `/health` remains a light process check. Signed `/health/ready` also checks the database. Gateway failures return an explicit temporary-unavailability response instead of forwarding a redirect loop. Requests are not retried automatically.

`wrangler.jsonc` retains a 10 ms CPU limit and the existing account plan. Pages Functions share the account's Workers request allowance; no paid subscription or capacity upgrade was added. The gateway serves ordinary GETs for approved hashed JS/CSS/WOFF2 files and the versioned walkthrough poster from the native Pages `ASSETS` binding, with immutable caching, browser security headers and conditional responses. Visitor credentials are not sent to the asset store. A missing file or asset-store error falls back to the signed origin for public GET only; API mutations and inference are never retried. HEAD, range requests and the lazy-loaded MP4/WebM keep the existing signed origin handler: live verification showed the Pages binding did not preserve their metadata/range contract. HTML, release markers, readiness and private APIs always use the actual application, so static files cannot conceal origin failure.

After the normal frontend build, `node scripts/package-edge-release.mjs <revision>` creates a fresh `.local/edge-release/site` containing only approved public bytes, the revision-stamped Worker and a 404 document. It never uploads the application HTML, settings, source maps or credentials. The sibling manifest records SHA-256 hashes. CI retains this as `verified-edge-release`; edge-only changes skip the Hostless publish and paid macOS journey. Promote the checked `site` directory to the existing `dexter-onboardflow` Pages project using its existing local authentication, production branch `main`, and the exact checked commit. Do not upload the manifest directory or reuse an output directory with stale files. The `X-OnboardFlow-Asset-Source` and `X-OnboardFlow-Asset-Revision` response headers identify native asset delivery and its checked revision; `/release.json` continues to identify the stable backend release.

Future app releases also produce a matching public-asset package. Promote it alongside that release to retain the faster delivery; until promotion, missing new hashes safely use the signed origin. Old HTML hashes and rollback must retain this fallback. Keep the private key in the existing server-secret binding; never copy it into an upload or CI. A local recovery copy is encrypted with Windows DPAPI.

Asset-only verification uses `npm run test:edge`, `node --test scripts/package-edge-release.test.mjs`, frontend build/typecheck, unchanged-byte checks and connected Chrome for first loading, fonts, recording playback, navigation, source inspection, manual save/reload and reset. No AI is invoked. After promotion verify native asset headers/hashes, HEAD/conditional/video ranges and the unchanged signed ingress/session/storage checks. Application/model changes retain their separately authorised regression and inference acceptance. Availability monitoring uses one external UptimeRobot monitor for the public demo, following redirects at five-minute intervals and emailing DOWN/RECOVERY events. The older GitHub Demo availability workflow is manually disabled to avoid duplicate monitoring. Native Hostless HTTP `/health` checks every 10 seconds retain restart protection.
